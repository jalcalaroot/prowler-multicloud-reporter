# prowler-multicloud-reporter

Renamed from `prowler-multicloud-agent` on 2026-09-08 — per the user's own observation, a fixed deterministic pipeline (scan → normalize → compute score/compliance/trend → 2 narrowly-scoped LLM calls for prose → publish) with no planning loop, no autonomous tool use, and no decision-making isn't an "agent" in any technically honest sense, and shouldn't be named like one. GitHub repo renamed (`gh repo rename`), local remote updated, and both `infra/aws`'s trust policy and `infra/azure`'s federated credential updated in-place to the new OIDC subject (GitHub's OIDC repo-id stays stable across a rename, but the name segment embedded in a customized subject updates to the new name — see gotchas). Cloud resource names (`prowler-multicloud-agent-ci` IAM role, `rg-prowler-multicloud-agent` resource group, etc.) were deliberately **not** renamed to match — doing so would force real resource destroy/recreate for a cosmetic reason alone, which wasn't asked for.

Runs [Prowler](https://github.com/prowler-cloud/prowler) across AWS, Azure, and GCP from one GitHub Actions workflow, merges the findings into a common schema, and delivers three audience-tiered reports (dev/manager/exec) as a private, time-limited storage link (S3 on AWS, Blob on Azure, GCS on GCP) — AI-written where it matters. The only AI backend (since 2026-09-08) is **`llamafile`**: a small open-weight model running entirely on the GitHub Actions runner, so real vulnerability findings never leave the runner at all, not even to a first-party cloud model — see the design-decision bullet below for why. Amazon Nova (Bedrock) and Azure OpenAI's `gpt-4.1-mini`, both used successfully earlier in this project's life, were removed entirely (code + Terraform resources + variables) on 2026-09-08, not just disabled — see Status for that decision. Built to fill a gap validated against existing prior art (Prowler Cloud/Pro, awslabs/aws-security-assessment-solution, aws-samples/multi-account-security-assessment-via-prowler — none combine real multi-cloud coverage with an audience-tiered narrative delivered straight to the people who need it; the comparison itself was cut from the README on 2026-09-08 at user request to keep it purely technical).

Sibling to the `jalcalaroot` AWS/Azure ecosystem (`jalcalaroot-aws-bootstrap`, `jalcalaroot-azure-bootstrap`, `aws-vpc`, `azure-virtual-network`). Unlike those, it owns three small self-contained Terraform configs (`infra/aws/`, `infra/azure/`, `infra/gcp/`) rather than relying on the bootstrap repos — the point of this tool is that anyone adopting it (any company, any account) can bootstrap what it needs from a handful of variables, not just `jalcalaroot`'s own account. Applied directly, no CI/PR pipeline around it — see "IAM/security conventions" below.

## Design decisions worth knowing before changing anything

- **GitHub Actions is the only orchestrator.** No Lambda, no Azure Function, no dedicated database, no bot — deliberately, per the user's "simplify, needs to work ASAP" direction (2026-09-05). A chat-with-your-findings interface is still scoped as phase 2, not started. The persistent findings store is no longer hypothetical, though: `publish_reports.py` writes both `runs/<run_id>/findings.normalized.json` (history) and a stable `latest/findings.normalized.json` pointer, and `fetch_previous_scan.py` reads that pointer back on the *next* run (2026-09-06) — no separate database, just one well-known object key doing the job of a "last run" table.
- **Risk score, compliance %, and trend are computed deterministically, never by the LLM.** All three (`generate_report.py`) are plain arithmetic over the findings — the LLM only narrates around numbers that already exist, never invents or computes them. This matters specifically for the score: it has to be reproducible run-to-run on identical input, which an LLM asked to "rate this 0-100" would not reliably give you, and the whole point of tracking a score over time breaks if it drifts for reasons unrelated to the underlying findings.
- **The risk score formula is normalized by total checks, not absolute severity counts** — an earlier version wasn't, and returned 0/F on every real scan regardless of how bad or good the account actually was (caught by testing against a real 180-check scan on 2026-09-06, not found by inspection). A bigger scan naturally has more absolute failures than a smaller one at the same failure *rate*; dividing the weighted penalty by `total_checks` before scaling fixes that. See the `RISK_SCORE_SCALE` comment in `generate_report.py` for the actual numbers this was tuned against.
- **Compliance percentages are computed from this project's own PASS/FAIL findings, not Prowler's own compliance reports.** `COMPLIANCE_FRAMEWORKS` in `generate_report.py` matches by *prefix* against each finding's compliance-tag list (e.g. `"PCI-"` catches both `PCI-3.2.1` and `PCI-4.0`) and reports (checks passing / checks tagged) — this is a coarser measure than Prowler's own per-control-ID compliance CSVs, and is documented as an approximation, not a substitute for an actual audit. The exact framework key strings (`PCI-4.0`, `HIPAA`, `AWS-Foundational-Security-Best-Practices`) were confirmed against a real unfiltered AWS scan on 2026-09-06. **Labels are the real standard names, not generic placeholders** — the user explicitly pushed back on this (2026-09-08) after noticing "Azure Best Practices" implied a Microsoft-branded standard that doesn't exist: Azure has no AWS-style curated "foundational security best practices" framework of its own in Prowler, so the label is now **"CIS Azure Foundations Benchmark"**, matching what the tags actually are (`CIS-<version>`, e.g. `CIS-2.0`..`CIS-6.0` — no `-Azure` in the key at all, confirmed against a real Azure scan on 2026-09-08; the original `CIS-Azure` guess was wrong and never matched anything).
- **The only delivery mechanism is a private storage link (S3, Blob, or GCS) — no email.** Email (`scripts/send_email.py`, plain SMTP) was built on 2026-09-05, then deliberately removed on 2026-09-06 once link delivery covered the same "final client just needs a URL" need without a second mechanism to maintain, document, and secure credentials for. The bucket/container (`infra/aws`, `infra/azure`, `infra/gcp`) is **never public** — `scripts/publish_reports.py` generates time-limited signed URLs instead. This was also a pushback on the user's first framing ("a public endpoint in S3"): real vulnerability findings sitting permanently discoverable on the open internet is a bigger risk than the convenience is worth, and a signed link gives the same "just a URL" experience without it. A lifecycle rule also auto-expires objects (default 30 days) so old scans don't accumulate indefinitely either.
- **Three separate reports (dev/manager/exec), not one file with sections.** The very first cut put everything in one `report.html`; the user explicitly wanted per-profile documents instead (2026-09-05), so `generate_report.py` now writes `report-dev.html` (full table, no AI), `report-manager.html` (AI summary + top-10 table), `report-exec.html` (AI summary only). Two separate LLM calls per run (manager + exec), each with its own audience-specific prompt and independent fallback — not one call reused for both.
- **Each cloud's LLM is that cloud's own first-party model — not Claude on either, and deliberately not the same model on both.** This replaced an earlier design (Claude on Bedrock + Claude on Microsoft Foundry, "same model on both clouds") on 2026-09-06, after the user watched that design hit three separate friction points on Azure alone (manual Marketplace terms, an `azapi_resource` workaround, and a hard `InsufficientQuota` failure on a fresh subscription) and asked, correctly, "the whole point was that this should be easy for anyone to turn on — why is a customer going to hit any of this?" AWS runs → **Amazon Nova Pro** (`LLM_BACKEND=bedrock`, `amazon.nova-pro-v1:0`, invoked directly — no inference profile, no access request, confirmed working immediately on a real account with zero prior Bedrock configuration). Azure runs → **Azure OpenAI `gpt-4.1-mini`** (`LLM_BACKEND=azure-openai`) — Microsoft's own resource type, no Marketplace terms, and confirmed for real to already carry non-zero default quota (200 `GlobalStandard` units) on a fresh subscription. The unifying principle is no longer "same model everywhere" — it's "whichever model that cloud will hand you with zero friction," which turned out to be a genuinely different (and better) design than what "same model, two clouds" first suggested.
- **Azure OpenAI auth is Entra ID, not an API key.** `_call_azure_openai` uses the official `openai` SDK's `AzureOpenAI` client, authenticated with a `DefaultAzureCredential` token (falls back to `AZURE_OPENAI_API_KEY` only if explicitly set) — same "no static credentials" posture as everywhere else in this project.
- **`LLM_BACKEND=llamafile` is the project default (changed 2026-09-08), overriding the "each cloud's own first-party model" default above.** The user's own framing, after Nova/Azure OpenAI were already working end-to-end: "por seguridad que esa info salga es un tema" (real vulnerability data leaving the runner is a security concern, even to a free/first-party API). `enable_bedrock_access` (`infra/aws`) and `enable_openai` (`infra/azure`) both default to `false` now — the CI role/identity doesn't get Bedrock/OpenAI access at all unless someone deliberately opts back in by setting both the Terraform var and `LLM_BACKEND`. llamafile runs `Llama-3.2-3B-Instruct` (Q4_K_M, 2.33GB) as a local OpenAI-compatible server (`scan.yml` downloads + starts it before `generate_report.py` runs) — `llm_client.py`'s `_call_llamafile` just points the existing `openai` SDK at `127.0.0.1:8080`. Honest tradeoff, not hidden: a 3B CPU model's prose is noticeably weaker than Nova Pro/gpt-4.1-mini, and the run takes ~6-7 extra minutes for the model download + CPU inference. Two real quality bugs were found and fixed testing this for real (2026-09-08): llama.cpp's server emitted the model's own `<|eot_id|>` end-of-turn token as literal trailing text instead of a hidden stop marker, and the model sometimes echoed the instruction back as a preamble ("Here is a 2-3 sentence executive summary:") before the actual content — both cleaned up defensively in `_call_llamafile`. **Update, same day:** once llamafile was validated end-to-end from a completely clean infra rebuild (see Status), the user asked to remove Nova/Azure OpenAI entirely rather than leave them disabled-but-present — `enable_bedrock_access`/`enable_openai` and the resources/code they gated no longer exist at all, not just default-off. `llm_client.py`'s `summarize()` now calls llamafile directly, no backend dispatch.
- **Storage delivery is backend-agnostic.** `scripts/publish_reports.py`/`storage_backend.py` pick S3, Azure Blob, or (added 2026-09-08) GCS via `STORAGE_BACKEND` (default `s3`) so the same 3 links come out regardless of which cloud hosts them — the user's original framing was "S3 for AWS, Blob for Azure" (2026-09-06), implemented as one module with one function set per backend rather than separate scripts, and the same shape extended cleanly to a third cloud without restructuring anything.
- **The LLM never sees raw findings or cloud access.** `generate_report.py` computes aggregates first; only the counts + a short top-findings list go into the prompt, with a system prompt forbidding invented findings or changed severities. If the call fails for any reason (including "model access not granted yet" — see gotcha below), it falls back to a templated summary rather than failing the report.
- **Read-only by construction.** Prowler itself never writes to the scanned account. The eventual CI role for the AWS leg should be `SecurityAudit` + `ViewOnlyAccess` managed policies (least privilege) — **not** `AdministratorAccess`, even though the account currently used for local testing has that attached (pre-existing, not something this project should rely on or expand).
- **Setup (creates infrastructure) and Run (uses it) are a hard line, and only one side is automatable.** `terraform apply` always needs a human to type it directly — no in-chat authorization substitutes, and this isn't a Claude Code quirk specific to this project: `jalcalaroot-aws-bootstrap`/`jalcalaroot-azure-bootstrap` hit the identical constraint, they just never notice it day-to-day because their real applies happen inside `terraform-apply.yml` on merge to `main`, not via an agent running `terraform apply` locally — the human's authorization *is* the PR merge, not a chat message. This repo deliberately skipped that PR/CI pipeline (2026-09-05 call, see below), which means the same authorization has to happen as a literal terminal command instead. Once setup exists, though, Run (scanning + generating reports + uploading to a bucket that already exists) touches nothing new and needs no further authorization — confirmed for real 2026-09-06, see Status.

## IAM/security conventions inherited from the rest of the ecosystem

- **IAM/RBAC changes go through Terraform (`infra/aws/`, `infra/azure/`, `infra/gcp/`), never raw CLI** — same rule as `jalcalaroot-aws-bootstrap`/`jalcalaroot-azure-bootstrap`, applied here via this repo's own small configs instead of those repos', since the goal is a bootstrap any adopter can run standalone. Explicitly **not** wrapped in the tflint/Checkov/PR-plan-bot pipeline the Terraform infra repos use — the user's call (2026-09-05): this is a one-time, low-churn bootstrap step, not something that warrants that overhead.
- **Confirm before applying — but the classifier's actual line is "creates something new", not "touches real infra" in general.** The very first `terraform apply` for both `infra/aws` and `infra/azure` (real IAM/RBAC/storage resource creation) was blocked, and editing the classifier's own settings to loosen this was also blocked (it protects its own configuration, which is the point) — both correct, not bugs to route around. But later in the same day, in-place *modifications* to already-created resources (updating the IAM role's trust policy, swapping the Bedrock IAM policy from Claude to Nova, replacing the whole Claude-on-Foundry Azure stack with Azure OpenAI — a real 3-create/1-change/3-destroy apply) all went through without being blocked, while `az policy exemption create` (a genuinely new object, just a narrowly-scoped one) was blocked again. The practical rule that matches what was actually observed: the user runs the *first* `terraform apply` per environment (and any brand-new resource type after that); once something exists, iterating on it is not gated the same way.
- AWS role permissions: `SecurityAudit` + `ViewOnlyAccess` managed policies, `s3:PutObject`/`s3:GetObject` on exactly the reports bucket — never `AdministratorAccess`. No Bedrock/AI permissions of any kind (removed entirely 2026-09-08, see Status — the AI summary needs no cloud access at all now).
- Azure identity permissions: `Reader` on the subscription, `Storage Blob Data Contributor` scoped to exactly the reports storage account — never `Contributor`/`Owner`. No Cognitive Services/OpenAI permissions (same removal, same date).
- GCP identity permissions (added 2026-09-08): `roles/viewer` on the project, `roles/storage.objectAdmin` scoped to exactly the reports bucket, and `roles/iam.serviceAccountTokenCreator` granted to the service account **on itself** (self-impersonation, not a broader privilege) so it can sign GCS V4 URLs via the IAM Credentials API without ever holding a private key — never `roles/editor`/`roles/owner`.
- **gitleaks** (CI workflow + pre-commit) is the only secret-scanning coverage — this is a private repo, so GitHub's native secret scanning needs Advanced Security and isn't available (same confirmed limitation as the other private repos in this ecosystem).
- **Dependabot** covers `pip` (`scripts/requirements.txt`) and `github-actions`.
- Every third-party GitHub Action in `.github/workflows/` is pinned to a full commit SHA (not a mutable tag) — supply-chain hardening, matching the 2026-09-05 pass done across the rest of the ecosystem.

## Known gotchas

- **A GitHub account can customize its OIDC `sub` claim to use immutable numeric IDs instead of org/repo names**, and `AssumeRoleWithWebIdentity` fails with a generic "Not authorized" error against a trust policy that looks completely correct if this is on and unaccounted for. Confirmed for real (`gh api repos/<org>/<repo>/actions/oidc/customization/sub`) — this account's actual subject is `repo:<org>@<org-id>/<repo>@<repo-id>:*`, not the plain `repo:<org>/<repo>:*` the trust policy first assumed. Same gotcha already documented in `jalcalaroot-aws-bootstrap`'s own CLAUDE.md; `infra/aws`'s `github_subject_prefix` variable exists specifically so this is configurable instead of hardcoded, and the fix (updating an existing role's trust policy) was a plain in-place Terraform update, not new resource creation. **The IDs are stable, the name isn't**: renaming the GitHub repo (`prowler-multicloud-agent` -> `prowler-multicloud-reporter`, 2026-09-08) kept the same org id and repo id but the name segment embedded in the customized subject updated to the new name — `gh api .../oidc/customization/sub` needs re-checking after any repo rename, and both `infra/aws`'s trust policy and `infra/azure`'s federated credential need re-applying (in-place, not blocked) with the new value or every subsequent workflow run fails auth.
- **A GitHub repo rename can also break `actions/download-artifact@v4` with `Unable to download artifact(s): ... (403) Forbidden`, separately from the OIDC gotcha above** — confirmed for real on the rename to `prowler-multicloud-reporter` (2026-09-08), twice, a few minutes apart. The artifact and the plain REST API (`gh api repos/<org>/<repo>/actions/artifacts`, and a direct `.../artifacts/<id>/zip` download) both worked fine the whole time with a personal token — only `download-artifact@v4`'s own internal call (a newer Actions Results service, authenticated by the workflow's own short-lived runtime token, not the REST API) 403'd. Diagnosis before fix: hit the REST API directly first to confirm the artifact itself isn't the problem, rather than assuming a code bug. Fix was just waiting (~20 minutes resolved it here) and retrying with no code changes — read as GitHub-side propagation lag for that specific backend after a rename.
- **GitHub Actions sets an unset `vars.*` as an empty string in the job environment, not an absent variable.** `os.environ.get("KEY", default)`'s default only applies when the key is missing entirely — an explicit `os.environ.get("KEY") or default` is needed wherever a workflow-supplied env var might be legitimately unset (`REPORT_URL_EXPIRY_SECONDS`, `AZURE_STORAGE_CONTAINER`). Found this by actually triggering `scan.yml` for real and watching `publish_reports.py` crash with `ValueError: invalid literal for int() with base 10: ''` — would not have been caught by any local testing, since local runs never pass an env var as an empty string, they just omit it.
- **`--status FAIL` breaks compliance percentages.** Every demo scan before 2026-09-06 was run with `--status FAIL` to keep the sample output small, which means those files contain zero PASS findings -- computing a compliance % from FAIL-only data always gives 0%, which looks like a bug but is actually just missing data. `scan.yml`'s real "Run Prowler (live)" step was never filtered this way (it exports both), so this only ever bit local manual testing -- worth remembering if a future demo run looks suspiciously all-red.
- **Prowler's PyPI package (`prowler-cloud`) caps out below Python 3.14** — every release from 5.31 onward requires `>=3.10,<3.14`. This sandbox only has Python 3.14 installed, so `pip install prowler-cloud` fails at import time with a pydantic v1 `ConfigError` (an old 3.11.3 release gets silently resolved instead, which is incompatible in a different way). **Fix: always run Prowler via its official Docker image (`prowlercloud/prowler:latest`), never `pip install` it directly** — sidesteps the interpreter version entirely. This is what `scan.yml` does.
- **The image name changed.** `toniblyx/prowler` was the old (pre-v4) community image. The current official image is `prowlercloud/prowler`. An earlier draft of `scan.yml` had this wrong; fixed 2026-09-05 after actually running a scan.
- **Prowler's default/native export is OCSF JSON (`--output-modes json-ocsf`), not a flat custom schema.** `scripts/normalize_findings.py` and `sample-data/*.json` are written against the real OCSF shape (`cloud.provider`, `cloud.account.uid`, `finding_info.analytic.uid`, `resources[0]`, `remediation.desc`, `unmapped.compliance`, etc.) — confirmed against a real scan output on 2026-09-05, not the guessed v3-style flat schema an earlier draft used.
- **Prowler writes `<output-filename>.ocsf.json`**, not the bare filename passed to `--output-filename` — `scan.yml`'s live-scan step renames the file immediately after so downstream steps (and the sample-data fallback path) can use one consistent filename.
- **Superseded but worth knowing (Claude-specific, no longer this project's path):** Bedrock gates non-Amazon models behind a per-account "Model access" grant even when `list_foundation_models` shows them (hit this with `anthropic.claude-sonnet-5`); newer Bedrock models beyond Nova often need an inference-profile ID, not the bare model ID, for on-demand `InvokeModel` (hit this with `anthropic.claude-sonnet-4-6`); Claude on Microsoft Foundry needed `azapi_resource` since native `azurerm_cognitive_account`/`_deployment` didn't support `modelProviderData`/`allowProjectManagement` ([hashicorp/terraform-provider-azurerm#31140](https://github.com/hashicorp/terraform-provider-azurerm/issues/31140)); that `modelProviderData` block silently auto-signs the Anthropic Marketplace commercial terms on apply; Claude-on-Foundry only worked in `eastus2`/`swedencentral`/`westus2`. None of this applies to Nova or Azure OpenAI, which is a large part of why the 2026-09-06 pivot happened.
- **Azure OpenAI model versions get retired from new-deployment eligibility over time.** Hit this for real: an older `gpt-4o-mini` snapshot (`2024-07-18`) failed `terraform apply`/`az cognitiveservices account deployment create` with `ServiceModelDeprecated`, even though `az cognitiveservices account list-models` still listed it with a *future* `deprecation.inference` date — that field tracks when *existing* deployments stop working, not whether the version is still eligible for a *new* one. Landed on `gpt-4.1-mini` (`2025-04-14`) instead, confirmed deployable for real. If this breaks again later, re-run `list-models` and pick a current, non-deprecated version rather than assuming the one in `variables.tf` still works.
- **Azure OpenAI quota is tracked per SKU, not per model** — `OpenAI.Standard.gpt-4o-mini` and `OpenAI.GlobalStandard.gpt-4o-mini` are two separate quota buckets on the same subscription, and one can be non-zero while the other is genuinely zero (confirmed for real: `Standard` had 200 units, `GlobalStandard` had 0, for the exact same model). `az cognitiveservices usage list --location <region>` shows both — check it before assuming a deployment will fail just because one SKU shows zero.
- **A subscription's "Allowed locations" governance policy can conflict with a region a specific model needs**, and the fix is a scoped `az policy exemption create` against just the one resource group that needs the exception — not widening the policy for the whole subscription. Hit this for real when this account's policy only allowed `eastus` but Claude-on-Foundry needed `eastus2`; moot now that Azure OpenAI (which works fine in `eastus`) is the model in use, but the exemption pattern is worth remembering if a future model/region combination hits the same wall. `az policy exemption create`, like `terraform apply`, is a real governance change and was blocked by the harness's classifier the same way — the user ran it directly.
- **RBAC role-assignment propagation for Cognitive Services can be slow or inconsistent for a personal Microsoft (MSA, e.g. `@hotmail.com`) account specifically** — granting yourself `Cognitive Services OpenAI User` for a quick local test failed with `PermissionDenied` for over 90 seconds even though the assignment existed and API-key auth against the exact same deployment worked immediately. Storage's `Storage Blob Data Contributor` propagated fine on the first try for the same account, so this seems specific to Cognitive Services' RBAC path, not RBAC in general. Not expected to affect the real managed identity in production (a service principal, not an MSA guest), but don't be surprised by a similar delay when testing manually.
- **Azure federated-credential `subject` is an exact string match**, unlike AWS's `StringLike` OIDC condition. `infra/azure` sets one credential for `repo:<org>/<repo>:ref:refs/heads/main` — a workflow run from any other ref/environment needs its own additional credential block.
- **Prowler's Azure leg runs natively on the runner (pip), not in Docker like the AWS leg — this was wrong in an earlier draft of this file, corrected 2026-09-08 after actually running a live Azure scan for the first time.** `--az-cli-auth` (confirmed via `prowler azure --help`, alongside `--sp-env-auth`/`--browser-auth`/`--managed-identity-auth`) needs the actual `az` **binary** reachable wherever Prowler runs — mounting `$HOME/.azure` into the `prowlercloud/prowler` Docker container is NOT enough, because the `azure-identity` SDK's `AzureCliCredential` shells out to `az account get-access-token` rather than reading the token cache file itself, and that image doesn't ship the CLI (confirmed: `AzureHTTPResponseError... AzureCliCredential: Azure CLI not found on path`). `--sp-env-auth` doesn't help either: this identity is OIDC/federated-credential-based by design (no client secret), and the bundled azure-identity 1.21.0's `EnvironmentCredential` only supports secret/certificate/username-password auth, not a federated-token-file (workload-identity) mode. Fix: run Prowler via `pip install prowler-cloud` directly on the runner instead of Docker for the Azure leg only (AWS leg is untouched, Docker there has no CLI dependency) — `ubuntu-latest` already ships `az`, and `azure/login`'s OIDC exchange already authenticated that exact CLI session, so `--az-cli-auth` just works with zero extra credential plumbing.
- **The `prowlercloud/prowler` Docker image runs as a non-root user**, so it can't `mkdir` inside a bind-mounted host directory owned by the runner's own user — failed with `PermissionError: [Errno 13] Permission denied: '/output/compliance'` on the first real live-AWS run. Fix: `chmod 777` the local `reports/` directory before mounting it (harmless on an ephemeral CI runner).
- **Prowler's own process exit code is nonzero (3) whenever it finds at least one FAILed check** — expected on literally any real account, not a scan error, but it was killing the `Run Prowler (live)` step before `normalize_findings.py`/`generate_report.py` ever ran. Fix: `|| true` after each `docker run`/native `prowler` invocation, and let the later `mv reports/<cloud>-findings.ocsf.json ...` fail loudly (missing file) if the scan genuinely produced no output.
- **`fail-fast: false` on a matrix job does NOT make `needs:` treat a partially-failed matrix as successful.** It only stops one leg's failure from cancelling the other — `build-report`'s `needs: scan` still saw the whole `scan` job as failed whenever exactly one cloud's leg failed (e.g. Azure not set up yet), so `build-report` was skipped entirely even with real, usable AWS findings sitting in the artifact. Fix: `if: ${{ !cancelled() }}` on `build-report`, plus building the `normalize_findings.py` file list dynamically (only the findings files that actually landed) instead of hardcoding both clouds.
- **`google-github-actions/auth`'s exported credential config file inherits the same non-root-container permission problem as `reports/` did on AWS/Azure** — confirmed for real on the first live GCP run (2026-09-08): `PermissionError[13]: Permission denied: '/tmp/gcp-adc.json'` inside `prowlercloud/prowler`, because the file lands on the runner readable only by the runner's own user. Fix: `chmod 644 "$GOOGLE_APPLICATION_CREDENTIALS"` before mounting it into the container, same spirit as the `reports/` fix.
- **`google-cloud-storage`'s `download_to_filename()` does NOT create the destination file before raising `NotFound` on a missing object**, unlike `boto3`'s S3 download or the Azure Blob SDK (both open the destination file for writing before the request, so it exists, empty, when a 404 happens). `storage_backend.py`'s `_download_gcs` originally assumed the S3/Blob behavior and called `os.remove(local_path)` unconditionally in the `except NotFound` branch, which crashed with `FileNotFoundError` on literally the first scan ever for a project — exactly the "no trend history yet" case this whole code path exists to handle gracefully. Fix: check `os.path.exists()` before removing.
- **GCP's Workload Identity Federation can match its trust condition on the GitHub repo's immutable numeric id (`assertion.repository_id`) instead of its name (`assertion.repository`)** — `infra/gcp`'s `github_repository_id` variable does this when set. This is a genuine improvement over AWS's and Azure's name-based OIDC trust, both of which broke for real on the 2026-09-08 repo rename and needed a manual Terraform re-apply to fix (see the OIDC-subject gotcha above) — GCP's equivalent trust, set up with `github_repository_id`, would have needed no re-apply at all for the same rename. Worth retrofitting to AWS/Azure if either ever gains an equivalent "match on a stable id" condition.
- **A destroyed `google_iam_workload_identity_pool` (and the provider inside it) doesn't actually disappear -- it soft-deletes for 30 days**, and a subsequent `terraform apply` trying to recreate one with the same pool/provider id fails with `Error 409: Requested entity already exists`, even though `gcloud iam workload-identity-pools describe` shows nothing when queried the normal way. Confirmed for real re-deploying `infra/gcp` a day after tearing it down (2026-09-09): `gcloud iam workload-identity-pools describe github-actions --project=<id> --location=global` revealed `state: DELETED`, `expireTime: <30 days out>`. Fix: `gcloud iam workload-identity-pools undelete` (and the same `providers undelete` for the provider inside it, which stays deleted independently even after the pool itself is undeleted), then `terraform import` both into state (`google_iam_workload_identity_pool.github` / `google_iam_workload_identity_pool_provider.github`, import ID is the full resource path) before the next `terraform apply` -- otherwise Terraform still tries to create them fresh and hits the same 409. This makes GCP's Workload Identity Pool behave like a GCP project itself (also a 30-day soft-delete) rather than like a plain resource -- worth remembering before any future `infra/gcp` teardown-then-redeploy cycle within 30 days of the teardown.
- **Azure's federated-credential OIDC subject customization gotcha hits harder than AWS's equivalent.** Same root cause as the AWS gotcha above (this account's real subject uses the `<org>@<org-id>/<repo>@<repo-id>` numeric-id form, not the plain name), but Azure's federated credential `subject` is an **exact string match** — no `StringLike`-style wildcard the way AWS's trust policy has — so a wrong prefix here fails *every single run*, not just an edge case. `infra/azure`'s `github_subject_prefix` variable (added 2026-09-08, mirroring `infra/aws`'s) exists for exactly this; confirmed for real via `AADSTS700213: No matching federated identity record found for presented assertion subject`.

Fix, confirmed twice now (2026-09-06 and 2026-09-08): `aws s3 rm s3://<bucket-name> --recursive` to empty it, then re-run `terraform destroy` — the bucket then deletes in ~1s. **Every future teardown should expect to need this same manual emptying step first** — it's not a one-off.
